# 전체 코드 리뷰

검토일: 2026-10-26 · 대상: Reading Desk 3.0.0 · 환경: macOS ARM64

## 디자인 기준 재적용

앞선 화면 수정은 Catalyst의 규칙을 일관되게 적용하지 못했다. 이후 공식 데모를 측정해 셸 256px/40px,
제목 20px/32px, 컨트롤 36px, 표와 필드 간격을 공용화했다. 서재·설정·통계의 `PageHeader`,
설명의 왼쪽 열과 입력의 오른쪽 열을 갖는 `SettingsSection`, 공용 `Table`·`Field`를 실제 화면에서 사용한다.
공식 UI Kit 소스 도입과 공개 레퍼런스 규칙 적용은 구분한다. 정확한 출처·수치·앱별 차이는
[디자인 시스템](design-system.md#적용-기준과-출처)에 기록한다.

## 화면 정리 후 현재 상태

사용자 범위에 맞춰 JSON 가져오기·평문 내보내기는 UI와 데스크탑 명령·저장소 구현에서 제거했다.
R04의 최초 원인과 당시 검증은 아래에 역사 기록으로 남겼으며 현재 제공 기능을 뜻하지 않는다.
잘못된 날짜·중복 ID 검증은 CRUD와 암호화 백업 덮어쓰기 경로에 유지한다.
삭제된 평문 명령이 데이터를 읽거나 바꾸지 못하는 회귀 검사도 추가했다.
디자인 기준과 번들 글꼴은 [디자인 시스템](design-system.md)을 따른다.

현재 변경 검증: 린트·타입·구조 검사(126개 모듈), 프런트엔드 99개, 데스크탑 23개, E2E 5개 통과.
개발·stable·Storybook 빌드를 통과했다. macOS 개발 앱을 다시 열어 JSON 버튼·저장 배지 제거,
번들 마루부리, 서재·설정의 두 열 배치를 확인했다. 입력·목록·통계의 도서 샘플은 별도 임시 서재를 사용했다.
기존 사용자 서재에 테스트 도서를 쓰지 않았다.

## 수정 반영 결과

2026-10-26 후속 수정에서 **R01–R08을 모두 반영했다.** 아래 최초 검토 내용은 수정 전 근거와 재현 기록으로 유지한다.

| 항목 | 반영한 수정 | 검증 |
| --- | --- | --- |
| R01 | 공통 달력 날짜 검증, 저장·폼 검증, 기존 잘못된 날짜 표시 방어, 앱 오류 복구 경계 | 달력 경계·원자적 가져오기 거부·기존 표 렌더링·오류 복구 테스트 |
| R02 | 공통 오버레이 훅, body 포털, 배경 inert, Tab 순환·초기 포커스·제거 시 복원·스크롤 잠금 | Modal/SidePanel·중첩·닫힌 형제·StrictMode 단위 테스트와 키보드 E2E |
| R03 | 열린 작업 중 새 패널 단축키 차단, 작은 창의 검색 영역 열기와 포커스 | 추가·수정 입력 보존, 대화상자 안 검색 단축키, 포커스 복원 E2E |
| R04 | 공통 JSON 한도, 내보내기 전 같은 권수·바이트 검증 | 5,000권 왕복·5,001권 거부, 정확히 10MiB 왕복·초과 거부·writer 미호출 |
| R05 | React Query 오류·로딩·빈 결과 분리, 재시도와 이전 통계/경로 표시 | 실제 QueryClient를 사용한 조회 실패·재시도·재조회 실패 테스트, 통계 E2E |
| R06 | 표지 실패 상태를 실패 URL에 연결 | 동일 카드의 실패 URL → 수정 URL 테스트 |
| R07 | 현재 목록과 무관한 주제 문자열 기반 색상 배정 | 필터·추가 페이지·순서·재호출·유니코드 테스트 |
| R08 | 미사용 Storybook 8 의존성 제거, 기존 10.x API 사용, 통계 스토리의 실제 쿼리 데이터 연결 | 타입·Storybook 정적 빌드 통과; 통계 스토리에 play 검증 추가 |

당시 R04 수정은 JSON 양방향 한도를 통일했으나 이후 해당 기능 자체를 제거했다.
아래 최초 검토는 제거 전 코드에 대한 기록이다. 암호화 백업은 계속 제공한다.

React Query v5는 유지했다. 도서 목록·통계·저장소 정보의 조회와 CRUD 캐시 무효화는 기존 체계를 사용한다.
R05는 Query의 오류 상태를 UI가 올바르게 처리하도록 수정한 것이다.

추가로 건너뛴 폼 테스트 5개를 활성화했다. 브라우저 기본 검증에만 막히던 URL·가격 오류는 폼 스키마로
검증하고 메시지를 표시하며, 제출 콜백은 폼 데이터만 전달한다.
E2E도 각 시나리오와 재시도마다 별도 Bun 프로세스·키·데이터/내보내기 폴더를 사용하고 종료 시 정리한다.

리뷰 수정 단계에서 실제 네이티브 GUI 키보드 점검, 신규 취약점 DB 감사와
강제 종료·디스크 부족·실제 OS 보안 저장소 거부 검증은 재실행하지 않았다.
이후 루트 정리에서 설정·보조 코드를 `tooling/`, E2E를 `tests/e2e/`, 생성물을 `build/`로 모았다.
이 단계에서 개발·stable·Storybook 빌드와 기존 99/24/5개 테스트, 커버리지·개발 서버 기동을 다시 확인했다.
삭제 항목과 현재 경로는 [구조 문서](architecture.md#프로젝트-루트-관리)를 따른다.
아래 최초 검토의 해당 운영 한계와 성능 측정 과제는 계속 남는다. 커밋·푸시는 하지 않았다.

## 최초 검토 결론 (수정 전)

단일 사용자 데스크탑 앱에 맞는 모듈 경계와 암호화 저장·복원 흐름은 갖추어져 있다.
현재 규모에서 모노레포로 나눌 이유는 부족하며, 기존 단일 패키지 구조를 유지하는 판단이 적절하다.
다만 **잘못된 날짜를 정상 데이터로 저장한 뒤 서재 렌더링이 실패하는 문제를 우선 수정해야 한다.**
키보드 오버레이 처리, JSON 입출력 한도, 통계 오류 표시에도 재현 가능한 문제가 있다.
기존 자동 검사가 모두 통과해도 아래 경계 조건은 잡히지 않았다.

| 우선순위 | 건수 | 의미 |
| --- | ---: | --- |
| P0 | 0 | 이번 검토에서 확인한 즉시 대응 대상 없음 |
| P1 | 1 | 정상 지원 경로를 통해 서재 화면 사용을 막을 수 있음 |
| P2 | 4 | 특정 작업·키보드 경로에서 기능 또는 오류 처리가 잘못됨 |
| P3 | 3 | 표시 일관성 또는 개발 도구 유지보수 개선 |

이는 확인한 문제의 분류이며, 보안 취약점이나 데이터 손실 가능성이 전혀 없다는 보증은 아니다.
이하 내용은 최초 리뷰 당시의 상태다. 현재 처리 결과는 위 수정 반영 표를 기준으로 한다.

## 검토 범위와 방법

- 현재 작업 트리 전체를 기준으로 `contracts`, `desktop`, `src`, `scripts`, E2E 및 빌드·테스트 설정을 검토했다.
  기준 HEAD는 `64f1b16`이며, 마이그레이션·암호화·모듈화·스타일 변경이 포함된 미커밋 상태가 대상이다.
- 저장소 수명, 키 보관, PIN, 명령 큐, 백업/덮어쓰기/초기화, 검증 스키마, SQL, UI 상태와 캐시,
  가상 목록, 공용 컴포넌트, 토큰/CSS, 모듈 규칙과 테스트를 확인했다.
- 실제 개인 서재와 개인 JSON을 읽지 않았다. 데이터 재현은 합성 도서와 메모리 SQLite를 사용했다.
  E2E는 프로젝트의 임시 암호화 저장소를 사용했다.
- 발견 사항은 **실행 재현**, **정적 확인**, **운영 검증 미실시**로 구분했다.
  줄 번호는 검토 시점 기준이며 이후 수정에 따라 달라질 수 있다.
- v1 JSON 변환, ISBN 스캐너, AI 실행은 합의된 후속 범위이므로 미구현 결함으로 집계하지 않았다.

## 최초 발견 사항 (수정 전 근거)

### R01 · P1 · 잘못된 날짜를 가져오면 서재 화면 렌더링이 실패한다

**근거**

- [저장 스키마](../desktop/library/book-schema.ts) 3–8, 22, 33행: 출판일과 구매일이 일반 문자열 검증만 받는다.
- [JSON 가져오기](../desktop/library/repository.ts) 163–181행: 해당 스키마로 생성하므로 잘못된 날짜도 저장된다.
- [날짜 표시](../src/shared/lib/format.ts) 14–21행: 유효하지 않은 `parseISO` 결과에 바로 `format`을 호출한다.
- [서재 표](../src/pages/library/components/BookTable.tsx) 36–37행 및
  [상세 화면](../src/features/books/components/BookDetailModal.tsx) 65–66, 78–79행이 이 함수를 사용한다.
  [앱 진입점](../src/app/main.tsx)에는 렌더링 오류를 복구하는 경계가 없다.

**실행 재현**

1. 현재 JSON 가져오기 명령에 아래 배열을 전달한다.
2. 가져오기는 성공한다.
3. 저장한 도서를 기본 목록의 `BookTable`로 렌더링하면 `RangeError: Invalid time value`가 발생한다.

```json
[{ "book_name": "날짜 검증용 가상 도서", "purchase_date": "not-a-date" }]
```

저장된 값이 남으므로 단순 재실행으로 원인이 제거되지 않는다. 잘못된 출판일은 상세 화면에서 같은 문제를 일으킨다.
이는 미래 v1 변환이 아니라 현재 지원하는 JSON 가져오기 경로의 문제다.

**수정 방향**: 저장 경계에서 실제 달력 날짜를 검증하고, 빈 값 처리와 지원 날짜 형식을 명확히 한다.
표시 함수도 유효하지 않은 값에 대체 문구를 반환해야 한다. 렌더링 오류 경계를 추가해 복구 동작을 제공한다.
잘못된 날짜 가져오기 거부·기존 데이터 유지·이미 저장된 잘못된 값 표시를 회귀 테스트로 확인한다.

### R02 · P2 · 모달과 사이드 패널이 키보드 포커스를 가두지 않는다

**근거**

- [Modal](../src/shared/ui/Modal.tsx) 74–91행: 처음 포커스를 옮기는 로직만 있고 Tab 순환 처리가 없다.
  33–36행의 포커스 트래핑 설명과 구현이 다르다.
- 같은 컴포넌트는 `isOpen=false`일 때만 이전 포커스를 복원한다. 조건부 렌더링으로 바로 제거되면
  해당 분기를 실행하지 않는다. 서재의 상세 모달이 이 방식으로 제거된다.
- [SidePanel](../src/shared/ui/SidePanel.tsx) 27–48행: 스크롤과 Escape만 관리하며 초기 포커스·순환·복원이 없다.

**실행 재현**: Modal의 마지막 버튼에서 Tab을 누르면 열린 대화상자 밖의 버튼으로 이동했다.
닫힌 SidePanel을 열어도 포커스가 바깥의 열기 버튼에 남았다.
화면은 대화상자를 보여주지만 키보드 사용자는 배경의 다른 작업에 접근할 수 있다.

**수정 방향**: 두 오버레이가 공유하는 포커스 관리 방식을 사용한다.
비활성·숨김 요소를 제외한 초기 포커스, Tab/Shift+Tab 순환, 배경 접근 제한,
조건부 제거 시 포커스 복원을 함께 다룬다. 기존 닫기·폼 동작을 유지하는 회귀 테스트가 필요하다.

### R03 · P2 · 수정 중 Cmd/Ctrl+N으로 추가 패널을 중복해서 열 수 있다

**근거**

- [서재 상태 훅](../src/pages/library/hooks/useLibraryWorkspace.ts) 22–25, 112–126행:
  편집/상세/삭제 상태와 무관하게 단축키가 `showAddPanel=true`를 설정한다.
- [서재 화면](../src/pages/library/Library.tsx) 187–205행: 추가·수정 패널을 별개 조건으로 렌더링한다.
- [BookForm](../src/features/books/components/BookForm.tsx)은 `book_name` 등 고정 ID를 사용하고,
  [SidePanel](../src/shared/ui/SidePanel.tsx)도 `slide-over-title`이라는 고정 ID를 사용한다.

**실행 재현**: `editingBook`이 있는 상태에서 Cmd+N을 전달하면 `editingBook`이 유지된 채
`showAddPanel`도 true가 된다. 두 폼과 대화상자가 같은 레이어에 생기고 ID도 중복된다.
독립적인 Escape·스크롤 처리도 여러 오버레이가 동시에 동작하는 상황을 고려하지 않는다.
별도 조합 재현에서는 닫힌 형제 오버레이의 effect가 열린 오버레이의 body 스크롤 잠금을 해제했다.

**수정 방향**: 서재의 작업 상태를 하나의 활성 오버레이로 제한하거나, 단축키에서 진행 중 작업을 검사한다.
입력 중인 폼을 임의로 버리지 않도록 하고, 열린 작업이 있으면 해당 작업을 유지한다.
Cmd/Ctrl+F도 접힌 검색 영역이나 열린 대화상자 상태에서 동작할 수 있게 함께 점검한다.
수정·삭제·상세 화면에서 단축키와 Escape를 사용하는 회귀 시나리오를 추가한다.

### R04 · P2 · 앱이 내보낸 JSON을 앱에서 다시 가져오지 못할 수 있다

**근거**

- [내보내기 명령](../desktop/application/command-service.ts) 83–87행: 도서 전체를 제한 없이 한 파일로 내보낸다.
- [가져오기](../desktop/library/repository.ts) 163–168행: 파일당 10MiB·5,000권으로 제한한다.
- 당시 `useImportBooks.ts` 11–15행도 10MiB를 제한했다. 이 훅은 현재 제거되었다.

**실행 재현**: 메모리 서재에 합성 도서 5,001권을 만든 후 현재 내보내기와 동일하게
`JSON.stringify(library.all(), null, 2)`로 직렬화했다. 크기는 2,653,335바이트로 용량 제한보다 작았지만,
빈 대상 서재로 가져오기는 `최대 5,000권의 도서 배열을 가져올 수 있습니다.` 오류로 거부되었다.
개별 도서 추가와 여러 차례 가져오기로 이 규모의 서재를 만드는 것은 허용된다.

**수정 방향**: JSON 교환 파일의 내보내기·가져오기 한도를 일치시킨다.
분할 내보내기 또는 검증된 상한 확대 중 하나를 선택하고, 현재 형식 왕복 조건을 명시한다.
암호화 백업이 별도로 있으므로 이 문제를 암호화 백업의 복원 실패로 혼동해서는 안 된다.
5,000/5,001권과 10MiB 경계에서 왕복 및 원자적 거부를 테스트한다.

### R05 · P2 · 통계 조회 실패가 빈 서재로 표시된다

**근거**

  `data`와 `isLoading`만 사용한다.

- [설정 화면](../src/pages/settings/Settings.tsx) 13–16, 34–35행도 저장소 경로 조회 오류를

**실행 재현**: 통계 훅들이 `isError=true`, `isLoading=false`, `data=undefined`를 반환하도록 하면
빈 서재 안내가 나오고 오류 안내는 없었다. 저장소 연결 실패가 데이터 부재로 오해될 수 있다.

**수정 방향**: 로딩·오류·성공한 빈 결과를 구분하고 재시도 동작을 제공한다.
이전 데이터가 있는 재조회 실패도 사용자가 알아볼 수 있게 표시한다.
최초 실패·재조회 실패·정상 빈 서재를 각각 테스트한다.

## 유지할 설계와 후속 검토

### 구조·타입·저장소

- `app → pages → features → shared`와 공통 계약의 실행 환경 분리가 명확하다.
  구조 검사는 현재 117개 TS/TSX 모듈의 경계·경로·순환 참조를 통과했다.
- 도서 검증을 거친 필드만 SQL에 사용하고, 값은 매개변수로 바인딩한다.
  정렬 필드도 허용 목록으로 제한한다. 검토한 현재 경로에서 문자열 입력을 SQL 명령으로 직접 실행하는 흐름은 찾지 못했다.
- 쓰기 실패 시 메모리 트랜잭션을 취소하는 구조와 단일 명령 큐를 유지하는 것이 좋다.
  JSON 가져오기와 덮어쓰기 복원은 전체 성공/실패 경계를 갖는다.
- 전체 SQLite 이미지를 매번 동기 암호화·저장한다. 개인 서재 PoC의 명시된 선택이며 현재 결함으로 집계하지 않았다.
  실제 예상 데이터량으로 CRUD 지연·최대 메모리·백업/복원 시간을 측정한 후 확장 여부를 결정해야 한다.
- 미사용 생산 경로인 `useBooks`와 `ColorQueue.enqueue` 등은 후속 정리 후보지만 이번 리뷰에서 삭제하지 않았다.

### 암호화·PIN·백업

- 저장소와 백업은 AES-GCM 인증 및 별도 문맥을 사용하고, nonce/salt를 새로 생성한다.
  백업 비밀번호 키와 기기 저장 키의 경계가 분리되어 있다.
- 저장소 잠금을 키 생성 전에 획득하며, 기존 vault의 키가 없으면 새 키로 대체하지 않고 실패한다.
  보안 저장소 접근 실패 시 평문 우회도 없다.
- 잠긴 상태의 데이터 명령을 중앙에서 거부하고, 복원에는 미리보기 토큰·기한·revision·현재 PIN 확인이 있다.
  초기화와 복원의 보존 범위도 코드와 문서에 구분되어 있다.
- PIN 재시도 횟수와 30초 제한은 프로세스 메모리에 있으므로 앱 재시작 시 초기화된다.
  PIN은 선택적 화면 잠금이라는 현재 설명에 맞춰 판단했으며 강한 기기 인증으로 평가하지 않았다.
  재시작을 넘는 제한이 필요하면 별도 제품 요구로 정의해야 한다.
- 백업 미리보기의 만료는 복원 시 검사하며, 만료된 복호화 목록을 즉시 지우는 타이머는 없다.
  이는 실행 중 메모리를 보호하는 암호화가 아니라는 현재 위협 범위와 함께 이해해야 한다.
- 네이티브 내보내기는 최종 경로에 직접 쓰며 vault와 같은 원자적 파일 교체를 사용하지 않는다.
  디스크 부족·프로세스 종료 때의 부분 백업 정리와 성공 응답 전 내구성은 별도 실패 주입 검증 대상이다.
  이번 검토에서는 해당 장애를 재현하지 않았으므로 확정 데이터 손실 문제로 집계하지 않았다.

### CSS·UI·배포 도구

- 토큰을 CSS 원본으로 두고 Tailwind와 차트가 참조하는 방향은 적절하다.
  공용 컨트롤과 인접 CSS Modules를 유지한다. 기능적 중복 때문에 SCSS를 추가할 필요는 없다.
- 레이아웃 수치와 별개로 오버레이의 포커스·스크롤 수명을 공용화하는 작업이 우선이다.
  가상 목록의 컨테이너 측정·열 수 계산을 CSS만으로 바꾸지 않는다.
- 페이지가 정적으로 import되고 기능 공개 진입점이 통계를 함께 노출한다.
  현재 빌드의 가장 큰 JS 청크는 687.31kB, gzip 197.93kB이며 500kB 경고가 발생한다.
  통계 화면을 필요할 때 로드하는 방안은 검토할 수 있지만, 이번에는 시작 지연이나 메모리를 측정하지 않았다.
- Node/Bun 고정과 패키징 Bun 교체 훅을 확인했다. 훅이 Electrobun 내부 파일 구조에 의존하므로
  SDK 갱신 시 실제 배포 산출물의 바이너리·메타데이터 검증을 계속해야 한다.
  이번 리뷰에서 신규 보안 공지 조회, 의존성 취약점 DB 감사, native/stable 재패키징은 실시하지 않았다.
- 기존 GitHub Pages 배포 워크플로는 삭제 상태이며 현재 대체 CI 워크플로는 없다.
  원격 배포를 재개할 때 로컬에서 사용하는 검사들을 CI에도 연결하는 것이 좋다.
